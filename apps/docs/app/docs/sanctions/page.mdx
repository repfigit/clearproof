# Sanctions Oracle

The sanctions components build a Poseidon Merkle representation and publish a root to an oracle. A non-membership proof establishes a relationship to that supplied tree; it is not a guarantee that all sanctions obligations have been satisfied.

## Current construction

The circuit uses a sorted-tree gap proof with depth 20, domain-separated Poseidon leaves, Merkle paths and range checks. The tree builder and witness generator must agree on leaf encoding, sorting and boundary handling.

## Update workflow

The repository contains automation for source retrieval, tree rebuilds and proposed updates. Operators must validate source provenance, unexpected changes, target networks and relay results. The presence of a scheduled workflow does not demonstrate that the current deployed root is fresh.

After a root update, relay it to every intended deployment and verify consistency. A successful local build is insufficient evidence of an on-chain update.

## Contract controls

The current oracle source includes an update cooldown, a leaf-count floor, nonzero-root validation, a configurable grace period, pause controls and a bounded history of 1,000 roots. These checks reduce particular operational risks; they do not establish source correctness.

A registry can reject a stale root through the oracle's freshness check. API and SDK integrations need their own complete verification context; current parity remains open.

## Evaluation

Use explicit test data for local scenarios. Do not treat offline sample addresses as a current sanctions list. Record source versions and observation times for any evidence that must be reconstructed later.
